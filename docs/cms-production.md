## 1. Current architecture

Astro 7 (`output: 'static'`) with `@astrojs/cloudflare` v14 adapter.

- `astro.config.mjs`: `site`, `trailingSlash: 'always'`, `output: 'static'`, `imageService: 'compile'`,
  `prerenderEnvironment: 'node'`, `react()` integration (editor/admin only), `sitemap()` filtered to exclude `/admin`.
- The **public site is fully prerendered** at build time (static HTML in `dist/client`); it is NOT a database-backed SSR app.
- **Admin + API run on-demand inside a single Cloudflare Worker** (the `@astrojs/cloudflare` server entrypoint `entry.mjs`),
  which also serves `dist/client` as static assets via an `ASSETS` binding generated by the adapter.
- The Worker carries all bindings: `DB` (D1), `MEDIA` (R2), `ASSETS`.
- Admin middleware (`src/middleware.ts`) protects `/admin/**` and `/api/admin/**`; public routes return `next()` untouched.

### Route map (intended production)

| Path | Kind | Runs where | Protected |
|---|---|---|---|
| `/` , `/to-observe-and-report/`, `/to-show-and-tell/` | static | build | no |
| `/to-observe-and-report/{slug}/`, `/to-show-and-tell/{slug}/` | static | build | no |
| `/images/{id}` | on-demand Worker route (`src/pages/images/[id].ts`, `prerender=false`) | Worker | no (public deliver) |
| `/admin/**` | on-demand Worker | Worker | yes (Access + JWT) |
| `/api/admin/**` | on-demand Worker | Worker | yes (Access + JWT) |

The public build gets CMS content from the **published snapshot** only (`pub_doc`), fetched at build time:
`src/lib/cms/build-content.ts` → `assembleArticles()` in `src/lib/content/article.ts` → `getStaticPaths()` on the two `[slug].astro` routes.

### Production build flow (as built today)

```
npm ci
npm run build          # astro build (needs local D1 file OR CMS_BUILD_SKIP=1)
```

At build time `build-content.ts` opens the **local** D1 SQLite state file directly
(`.wrangler/state/**/d1/*/*.sqlite`) via `@libsql/client`. In a fresh production builder this file does not exist,
so either a remote snapshot must be provided some other way, or the build fails loudly (
documented in §11). No secrets are baked into static assets.

## 9. Build / deployment flow

Deterministic pipeline (required):

```
git pull
npm ci
npm run build        # astro build; reads CMS published snapshots (see below)
npm test
node scripts/qa.mjs  # against the built preview (see §13/local)
<deploy dist>        # workers deploy / Pages / CI push
```

**Where D1 is queried:** only at **build time** by `src/lib/cms/build-content.ts` (published `pub_doc` only) and at
**request time** by the admin API + `/images/[id]`. Public page rendering never touches D1 at request time.

**R2 during build:** NOT required for a successful build. R2 is only read by `/images/[id]` at request time and written by
the admin upload endpoint.

**When D1 is unavailable at build:** the build **fails loudly** (by design, `build-content.ts` throws with a clear message,
or `CMS_BUILD_SKIP=1` builds the legacy-only site deliberately). This prevents “D1 down → build succeeds → CMS stories vanish
→ silent bad deploy”.

**Reproducibility:** currently the production build needs the local D1 file to exist. For CI this must change — see §11.

## 10. Publish → deploy flow (implemented code; production config pending)

Implemented locally/code:

```
Publish (admin Worker)
   → publishStory() commits pub_doc            [unchanged atomic UPDATE]
   → nextRevision() allocates monotonic rev    [UPDATE … RETURNING — atomic]
   → requestDeployment() inserts a durable `deploy_requested` row
   → githubDispatchTrigger() fires repository_dispatch (best-effort)
   → 200 { story, build: { triggered, revision, status, error? } }
```

- Publishing the CMS snapshot and deploying the static site are **separate events**. A trigger failure never undoes
  the publish (D1 is authoritative); it is surfaced as `build.triggered=false` and the deployment row stays
  `deploy_requested`.
- The GitHub Actions workflow (`publish-deploy.yml`) fetches the published snapshot, builds with
  `CMS_SNAPSHOT_FILE`, deploys via wrangler, and reports `building`/`deployed`/`failed` back to
  `POST /api/deploy/status/`.
- The editor shows a deployment note after publish; the dashboard lists deployment rows with current/behind state.

Production configuration still required (not created):

- `GITHUB_REPO` var + `CMS_DEPLOY_TRIGGER_TOKEN` secret (Worker) so publish can dispatch.
- `CMS_SNAPSHOT_URL`, `CMS_STATUS_URL` vars + `CMS_PIPELINE_TOKEN` secret (GitHub Actions).
- `CLOUDFLARE_API_TOKEN` + `CLOUDFLARE_ACCOUNT_ID` (GitHub Actions) for `wrangler deploy`.
- Confirm the `wrangler deploy --config dist/server/wrangler.json` path on the first rollout.

## 11. Build-time CMS content — D1/build boundary (implemented code; production config pending)

Today `build-content.ts` supports two sources:

1. **Local dev:** reads `.wrangler/state/**/d1/*/*.sqlite` via `@libsql/client` (unchanged default).
2. **CI/remote:** reads a published-content snapshot file pointed at by `CMS_SNAPSHOT_FILE`. The snapshot is produced
   by `GET /api/deploy/snapshot/` (Bearer `CMS_PIPELINE_TOKEN`), which serializes exactly what `listPublishedStories()`
   returns plus the current monotonic `revision`, so D1 stays the source of truth and validation cannot drift.

Failure policy is shared and loud: missing/unreadable source or malformed/`missing title or body` story fails the
build (no deployment). `CMS_BUILD_SKIP=1` builds legacy-only deliberately.

Deferred production config: the snapshot endpoint's `CMS_PIPELINE_TOKEN` secret and the workflow secrets above.

## 16. Rollback strategy

- **Site:** previous `dist`/Worker deployment is re-promotable (Pages/Workers keep prior versions); re-deploy prior build.
- **Content:** D1 `pub_doc` is the only public source — a bad publish can be reverted by publishing the previous snapshot or
  editing + republishing; legacy 35 articles live in `src/data/site.json` and are unaffected by any D1 state.
- **Data safety:** never destructive-migrate; new migrations are additive only. `images` blobs are immutable + content-hashed.

## 17. Audit findings — status after blocker fixes

### FIXED — admin editor and preview pages now render (was: empty document)

Root cause: `edit.astro`/`preview.astro` used bare `<editor-wrapper client:only="react">` / `<preview-wrapper>` tags without
importing the React components, so Astro compiled the island with a `null` component reference and the SSR streamed an empty
document; no editor JS was emitted to `dist/`.

Fix (`fix: mount cms editor react islands`):
- Imported `EditorWrapper`/`PreviewWrapper` in the `.astro` pages and mounted them as `<EditorWrapper client:only="react" …>`
  with camelCase props (`storyId`, `initialDoc`, `initialRev`).
- `.astro` check now resolves the components; `EditorWrapper.*.js` / `PreviewWrapper.*.js` islands are emitted and contain
  Tiptap code (verified: `tiptap`/`useEditor` strings present in the compiled client bundle).
- The editor's save path now goes through the real API (`PUT /api/admin/stories/:id/draft/`) instead of calling Worker-only
  `getEnv()`/`saveDraft(env.DB)` from browser code; autosave title/subtitle persist to D1.
- `@tiptap/suggestion` (v3) is used as a plugin factory inside an `Extension.addProseMirrorPlugins()` wrapper (its `.configure`
  API no longer exists), and `StarterKit`'s built-in `link` is disabled to match the custom `Link` configuration.
- `useAutosave` reads fresh state via refs so a debounced save never persists stale title/subtitle.

Regression coverage:
- `scripts/editor-regression.mjs` — boots the dev server and asserts edit + preview render (non-empty body, editor root,
  title/subtitle inputs, Tiptap contenteditable, ProseMirror, Publish button, autosave persists, no console/page errors).
- Verified in a real browser at 390/768/1024/1380: no horizontal overflow, no broken targets, no console errors.

### FIXED — image upload now works and cleans up on failure (was: 500 always / R2 orphans)

Root cause: the upload endpoint stored `width = 0; height = 0`, violating the schema's `CHECK (width > 0)` / `CHECK (height > 0)`,
and the R2 `put()` ran before the D1 insert — so every upload 500'd and left an orphan object in R2 when the insert failed.

Fix (`fix: validate image dimensions and cleanup failed uploads`):
- Added `src/lib/cms/image-info.ts`, a dependency-free JPEG/PNG/WebP header reader that returns real width/height and the
  detected MIME. It runs in the Worker runtime (workerd) where the native `sharp` binary is unavailable; the project's
  `sharp` image pipeline runs only at build time in Node.
- Upload now validates the **actual file structure** (renamed text / malformed binary / MIME mismatch all rejected 422)
  before any storage happens, keeps the database CHECK constraints intact, and stores real dimensions.
- Storage order is now: validate → read header → dedupe → R2 `put` → D1 insert → on insert failure, `R2.delete(key)` with a
  logged cleanup failure if the delete itself fails. No orphan objects remain after a failed upload.
- The 20 MB cap, declared-MIME allowlist, and sha256 dedupe are preserved.

Regression coverage:
- `src/lib/cms/images-endpoint.test.ts` — 11 endpoint-level tests through the **real** upload handler + real D1 schema
  (valid JPEG/PNG/WebP, dedupe, text-renamed/malformed/MIME-mismatch/oversized rejection, and an explicit R2-put→D1-fail
  cleanup test proving the R2 object is deleted).
- `src/lib/cms/image-info.test.ts` — header reader unit tests.
- Live verified: upload → real dims → R2 object → D1 row → `GET /images/{id}/` → 200, correct `Content-Type`, immutable
  cache headers, byte-identical body; unknown id → 404. A published CMS article referencing the image renders it in the
  static build and on the section archive.

### MEDIUM — publish does not trigger deployment, and the UI cannot tell

**Updated:** the publish endpoint now records a durable deployment request (monotonic revision) and fires a GitHub
`repository_dispatch` best-effort; the editor shows a deployment note and the dashboard lists deployment state. What is
still **not configured in production** (code exists): the Worker secrets/vars the trigger needs (`GITHUB_REPO`,
`CMS_DEPLOY_TRIGGER_TOKEN`, `CMS_PIPELINE_TOKEN`) and the GitHub Actions secrets, so in a fresh deployment publish will
report `build.triggered=false` until those are set. See §10/§11 and `docs/cms-publish-pipeline-design.md`.

### MEDIUM — remote build cannot read production D1 yet

**Updated:** `build-content.ts` now supports `CMS_SNAPSHOT_FILE` (a published-content snapshot from
`GET /api/deploy/snapshot/`), and the GitHub workflow uses it. Still required in production: `CMS_PIPELINE_TOKEN`
(Worker secret + Actions secret), `CMS_SNAPSHOT_URL`/`CMS_STATUS_URL` vars, and Cloudflare deploy secrets. The local
SQLite source remains the developer default. See §10/§11.

### LOW — `www` vs apex canonical unverified

Code canonicalizes to `www`; confirm a 301 and matching Access host rules at deploy time (§8). **Unchanged in this milestone.**
